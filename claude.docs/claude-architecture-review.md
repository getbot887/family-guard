# FamilyGuard 架构审查建议

> 针对 `architecture.md` v2.0 的审查意见
> 审查日期：2026-07-02

---

## 一、核心功能定位

项目核心功能：**家长端远程控制孩子手机上指定App的使用权限（允许/禁止）**。

所有设计决策应围绕此核心展开，非MVP功能建议延后。

---

## 二、关键问题

### 2.1 规则模型过于复杂

当前设计有四张关联表：`rules → rule_apps → rule_schedules → rule_devices`。

核心需求本质是："这几个App在什么时间段内不能用"。建议简化：

- 如果一个规则只针对一台设备，`rules` 表可直接包含 `device_id`，去掉 `rule_devices` 关联表
- 如果需要分组管理多台设备，保留 `rule_devices`，但需说明业务场景

---

### 2.2 规则同步实时性不足

文档说孩子端"定时轮询"拉取规则，但未定义轮询间隔。家长修改规则后，孩子端多久生效？

建议：

- **基础轮询 + 推送触发**：轮询间隔设为 15-30 分钟作为兜底，配合 FCM（Firebase Cloud Messaging）推送实现秒级生效
- 或使用 WebSocket 长连接实时下发
- 无网络时降级为本地缓存的最近一次规则

---

### 2.3 App识别方式未明确

`rule_apps` 只存了 `package_name`，但家长端UI需要显示App图标和名称。需要说明：

- App名称/图标的来源：孩子端上报已安装列表？还是维护一个公共App数据库？
- 孩子端卸载再重装后，`package_name` 不变，规则应自动生效
- 如何处理同一App的不同版本或变体（如微信分身）

---

### 2.4 缺少模式定义

文档只体现了"禁止列表中的App"，但实际场景可能需要两种模式：

| 模式 | 说明 |
|------|------|
| **黑名单模式** | 禁止指定App，默认允许其他所有App |
| **白名单模式** | 只允许指定App，默认禁止其他所有App |

两种模式对规则引擎和UI的影响不同，建议在设计阶段明确定义。

---

## 三、安全与稳定性

### 3.1 孩子端Token下发流程不清晰

`pairing_code` 的完整生命周期未说明：

- 如何生成（随机算法？长度？）
- 是否单次使用（用完即失效）
- 有效期多长
- 如何防止暴力尝试

### 3.2 事件查询路径效率低

家长端查看拦截记录需要 `events → devices → owner_id` 做JOIN。当events数据量大时性能差。

建议：events表增加冗余 `owner_id` 字段，或明确说明查询策略。

### 3.3 JWT Secret管理未说明

文档提到"HS256 + 随机Secret"，但未说明：

- Secret存储位置（环境变量？配置文件？）
- 是否需要轮换机制
- 孩子端和家长端是否共用同一Secret

### 3.4 本地规则缓存未加密

孩子端Room数据库缓存的规则，若设备被root可直接读取修改。建议使用 EncryptedRoom 或 Android Keystore 加密敏感数据。

## 四、防绕过策略补充

当前防绕过矩阵缺少以下场景：

| 绕过方式 | 当前状态 |
|----------|----------|
| 通过ADB禁用App | 未提及 |
| 安全模式启动 | 未提及 |
| 关闭无障碍服务 | 仅"定时检测"，未定义检测频率 |

建议补充：

- ADB：监听 `PACKAGE_CHANGED` 事件，检测到异常卸载/禁用时上报
- 安全模式：技术上难以防护，建议在文档中明确标注为已知限制
- 无障碍检测频率：建议每30秒检测一次，检测到关闭立即通知家长端

## 五、MVP精简建议

### 可延后的功能

| 功能 | 当前位置 | 建议 |
|------|----------|------|
| Web后台 | 第三节 3.3 | 删除或标注为远期规划 |
| `/events/stats` 统计API | 第四节 4.5 | 移至Phase 2 |
| 数据清理策略（90天归档） | 第七节 7.2 | 移至Phase 2 |
| API版本策略 | 第四节 4.8 | 简化为"当前v1，有breaking change时再升级" |
| fl_chart图表 | 第三节 3.2 | 移至Phase 2 |

### MVP核心功能清单

```
1. 认证：注册 / 登录 / Token刷新
2. 设备绑定：配对码绑定 / 解绑
3. 规则管理：创建规则（App列表 + 时间段） / 启用禁用 / 删除
4. 规则同步：孩子端拉取并缓存规则
5. 实时拦截：AccessibilityService + 全屏拦截页面
6. 事件上报：拦截记录上报 + 家长端查看
```

## 六、其他建议

1. **技术版本号**：建议标注"最低兼容版本"而非精确版本，避免文档过时
2. **监控告警**：补充后端健康检查端点和uptime监控方案
3. **备份策略**：明确PostgreSQL备份频率和恢复流程
4. **多家长场景**：一个设备能否被多个家长账号管理？需要提前考虑数据模型
5. **心跳间隔**：定义设备心跳频率（建议5分钟），超时判定离线的阈值（建议15分钟）
